# 🔥 CASE 1 — Prometheus + Grafana + Alertmanager

> **Build a production-grade metrics, dashboarding and alerting platform from nothing.** You'll instrument a real app, deploy the whole stack with Helm, write PromQL, define recording and alerting rules, route alerts to Slack, and finish with a working SLO and an HPA driven by a custom metric.
>
> **Time:** 6–8 hours · **Level:** complete beginner → confident operator
> **Prereq:** Docker, `kind` (or minikube), `kubectl`, `helm`. Read [01-OBSERVABILITY-GUIDE.md](./01-OBSERVABILITY-GUIDE.md) §1–§10 first, or skim it and come back.

## 1. Step 1 — Understand what you're about to install

`kube-prometheus-stack` is one Helm chart that installs **seven** things. Knowing what each one is saves you hours of confusion later.

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm show values prometheus-community/kube-prometheus-stack > kps-values-defaults.yaml
wc -l kps-values-defaults.yaml            # ~5,000 lines. Don't read it all — read §3 below.
helm search repo kube-prometheus-stack --versions | head -5
```

| Component | Kind | What it does | Port |
|---|---|---|---|
| **prometheus-operator** | Deployment | Watches the `Prometheus`, `ServiceMonitor`, `PrometheusRule`, `Alertmanager`, `PodMonitor`, `Probe` CRDs and **generates the config** | 8080 |
| **prometheus** | StatefulSet (+ PVC) | Scrapes, stores, evaluates rules | 9090 |
| **alertmanager** | StatefulSet | Dedups, groups, routes, notifies | 9093 |
| **grafana** | Deployment | Dashboards | 3000 |
| **kube-state-metrics** | Deployment | Kubernetes object state → metrics | 8080 |
| **prometheus-node-exporter** | DaemonSet | Host metrics on **every** node | 9100 |
| **prometheus-adapter** | Deployment | Serves Prometheus metrics through `custom.metrics.k8s.io` so **HPAs can use them** | 6443 |

Plus the CRDs it installs:

```bash
kubectl api-resources | grep -i 'coreos.com'
# alertmanagerconfigs      monitoring.coreos.com/v1alpha1   true    AlertmanagerConfig
# alertmanagers            monitoring.coreos.com/v1         true    Alertmanager
# podmonitors              monitoring.coreos.com/v1         true    PodMonitor
# probes                   monitoring.coreos.com/v1         true    Probe
# prometheuses             monitoring.coreos.com/v1         true    Prometheus
# prometheusagents         monitoring.coreos.com/v1alpha1   true    PrometheusAgent
# prometheusrules          monitoring.coreos.com/v1         true    PrometheusRule
# scrapeconfigs            monitoring.coreos.com/v1alpha1   true    ScrapeConfig
# servicemonitors          monitoring.coreos.com/v1         true    ServiceMonitor
# thanosrulers             monitoring.coreos.com/v1         true    ThanosRuler
```

> 🔑 **You will almost never edit `prometheus.yml` directly.** You create a `ServiceMonitor` and the Operator regenerates the config and reloads Prometheus. That's the whole point of the Operator. If you find yourself `kubectl edit`-ing the Prometheus ConfigMap, you're doing it wrong.

## 3. Step 3 — PromQL, hands on

Open **http://localhost:9090/graph** and type these. This is the fastest way to build PromQL intuition.

### 3.1 Orientation queries

```promql
up                                                    # every target: 1 = up, 0 = down
up == 0                                               # anything down (should be empty)
count(up)                                             # how many targets
sum(up) by (job) / count(up) by (job)                 # availability per job
{__name__=~".+", job="node-exporter"}                 # ⛔ don't do this — everything for a job
count({__name__=~".+"})                               # ⭐ the total number of series
```

### 3.2 Node metrics (node_exporter)

```promql
# CPU utilization — the correct formula
1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))
# → 0.31 = 31% busy

# per-core, to find a hot core
1 - avg by (instance, cpu) (rate(node_cpu_seconds_total{mode="idle"}[5m]))

# iowait — the "my disk is the bottleneck" signal
avg by (instance) (rate(node_cpu_seconds_total{mode="iowait"}[5m]))

# memory
node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes         # used, bytes
1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)   # used, ratio
node_memory_Cached_bytes / node_memory_MemTotal_bytes               # the page cache

# load per core (saturation, not utilization) ⭐
node_load15 / count by (instance) (node_cpu_seconds_total{mode="idle"})
# > 1.0 sustained = things are queueing

# disk
node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}
rate(node_disk_io_time_seconds_total[5m])                          # ⭐ disk busy ratio (saturation)
rate(node_disk_io_time_weighted_seconds_total[5m])                 # avg queue length
rate(node_disk_read_bytes_total[5m])                               # throughput
rate(node_disk_reads_completed_total[5m])                          # IOPS

# network
rate(node_network_receive_bytes_total{device!="lo"}[5m]) * 8       # bits/s in
rate(node_network_transmit_bytes_total{device!="lo"}[5m]) * 8      # bits/s out
rate(node_netstat_Tcp_RetransSegs[5m]) / rate(node_netstat_Tcp_OutSegs[5m])   # ⭐ retransmit ratio
rate(node_network_receive_errs_total[5m])

# file descriptors — the "too many open files" predictor
process_open_fds / process_max_fds

# ⭐ prediction: will this disk fill up?
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 24*3600) < 0
```

### 3.3 Container metrics (cAdvisor, from the kubelet)

```promql
# CPU per pod
sum by (namespace, pod) (rate(container_cpu_usage_seconds_total{namespace="shop"}[5m]))

# ⭐ memory — use working_set, NOT usage. working_set is what the OOM killer compares to.
container_memory_working_set_bytes{namespace="shop"}
container_memory_rss{namespace="shop"}                 # excludes the page cache

# memory as a fraction of the limit — the OOM predictor ⭐
container_memory_working_set_bytes{namespace="shop", container!=""}
  / on(namespace, pod, container) group_left
kube_pod_container_resource_limits{resource="memory"}
# > 0.85 = you're going to be OOMKilled soon

# ⭐ CPU THROTTLING — the latency killer almost nobody watches
sum by (namespace, pod) (rate(container_cpu_cfs_throttled_periods_total{namespace="shop"}[5m]))
  / sum by (namespace, pod) (rate(container_cpu_cfs_periods_total{namespace="shop"}[5m]))
# > 0.25 = ⛔ you're throttled a quarter of the time; your CPU limit is too low

# network per pod
sum by (namespace, pod) (rate(container_network_receive_bytes_total[5m]))

# filesystem
container_fs_usage_bytes{namespace="shop"}
```

### 3.4 Kubernetes state (kube-state-metrics)

```promql
# pods not in a good state
kube_pod_status_phase{phase!~"Running|Succeeded"} == 1

# ⭐ restarts — the crashloop detector
kube_pod_container_status_restarts_total > 3
increase(kube_pod_container_status_restarts_total[15m]) > 3       # ⭐ restarting RIGHT NOW

# why did the last one die?
kube_pod_container_status_last_terminated_reason
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} > 0

# deployment readiness
kube_deployment_status_replicas_available / kube_deployment_spec_replicas < 1
kube_deployment_status_replicas_available{namespace="shop"}
kube_deployment_status_condition{condition="Available", status="false"} == 1

# nodes
```

```java
package com.shop.service;

import io.micrometer.core.instrument.*;
import io.micrometer.core.instrument.Timer;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

import java.time.Duration;
import java.util.List;
import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.atomic.AtomicInteger;

@Service
public class OrderService {

    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    // ── 1. A COUNTER (with low-cardinality labels) ──────────────────────
    private final Counter ordersCreated;
    private final Counter ordersRejected;

    // ── 2. A GAUGE (backed by a live object) ────────────────────────────
    private final AtomicInteger pendingOrders = new AtomicInteger(0);

    // ── 3. A TIMER (= histogram + counter + summary in one) ⭐ ──────────
    private final Timer orderProcessingTimer;

    // ── 4. A DISTRIBUTION SUMMARY (a histogram of non-time values) ──────
    private final DistributionSummary cartSize;

    private final MeterRegistry registry;

    public OrderService(MeterRegistry registry) {
        this.registry = registry;

        this.ordersCreated = Counter.builder("shop_orders_created_total")
                .description("Orders successfully created")
                .tag("channel", "web")               // ⭐ bounded cardinality
                .register(registry);

        this.ordersRejected = Counter.builder("shop_orders_rejected_total")
                .description("Orders rejected")
                .tag("channel", "web")
                .register(registry);

        // ⭐ a gauge observes an object; it is NOT incremented
        Gauge.builder("shop_orders_pending", pendingOrders, AtomicInteger::get)
                .description("Orders awaiting payment")
                .register(registry);

        this.orderProcessingTimer = Timer.builder("shop_order_processing_duration_seconds")
                .description("Time to process an order")
                .publishPercentileHistogram()        // ⭐ emit histogram buckets
                .serviceLevelObjectives(             // ⭐ buckets at your SLO thresholds
                        Duration.ofMillis(100), Duration.ofMillis(250),
                        Duration.ofMillis(500), Duration.ofSeconds(1))
                .minimumExpectedValue(Duration.ofMillis(10))
                .maximumExpectedValue(Duration.ofSeconds(10))
                .register(registry);

        this.cartSize = DistributionSummary.builder("shop_cart_size_items")
                .description("Items per cart")
                .publishPercentileHistogram()
                .register(registry);
    }

    public record OrderResult(String orderId, String status, long amountCents, int items) {}

    public OrderResult createOrder(String customerTier, int items) {
        // ⭐ record the duration AND the outcome, with a bounded status tag
        return orderProcessingTimer.record(() -> {
            cartSize.record(items);

            // simulate work
            sleep(ThreadLocalRandom.current().nextInt(20, 300));

            if (ThreadLocalRandom.current().nextInt(100) < 4) {     // 4% failure
                ordersRejected.increment();
                // ⭐ a dynamic tag is fine ONLY if the value set is bounded
                registry.counter("shop_orders_failures_total",
                        "reason", "payment_declined",
                        "tier", customerTier).increment();
                return new OrderResult(null, "rejected", 0, items);
            }

            pendingOrders.incrementAndGet();
            ordersCreated.increment();
            sleep(50);                                              // "payment settles"
            pendingOrders.decrementAndGet();

            return new OrderResult("ord_" + System.nanoTime(),
                    "created", items * 1499L, items);
        });
    }

    /** ⭐ A manually-scoped timer, when you need to add tags at the end. */
    public OrderResult createOrderWithTags(String customerTier, int items) {
        Timer.Sample sample = Timer.start(registry);
        String outcome = "success";
        try {
            OrderResult r = createOrder(customerTier, items);
            outcome = "rejected".equals(r.status()) ? "rejected" : "success";
            return r;
        } catch (RuntimeException e) {
            outcome = "error";
            throw e;
        } finally {
            // ⭐ tags are applied when you STOP the sample, so you can use the outcome
            sample.stop(Timer.builder("shop_order_create_seconds")
                    .tag("outcome", outcome)
                    .tag("tier", customerTier)
                    .publishPercentileHistogram()
                    .register(registry));
        }
    }

    public List<String> getItems() {
        sleep(ThreadLocalRandom.current().nextInt(5, 60));
        return List.of("widget", "gadget", "doohickey");
    }

    private static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

```java
package com.shop.controller;

import com.shop.service.OrderService;
import com.shop.service.OrderService.OrderResult;
import io.micrometer.core.instrument.MeterRegistry;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.Map;
import java.util.concurrent.ThreadLocalRandom;

@RestController
@RequestMapping("/api")
public class OrderController {

    private static final Logger log = LoggerFactory.getLogger(OrderController.class);
    private final OrderService orders;
    private final MeterRegistry registry;

    public OrderController(OrderService orders, MeterRegistry registry) {
        this.orders = orders;
        this.registry = registry;
    }

    @GetMapping("/items")
    public ResponseEntity<?> items() {
        return ResponseEntity.ok(orders.getItems());
    }

    @PostMapping("/orders")
    public ResponseEntity<?> createOrder(@RequestBody(required = false) Map<String, Object> body) {
        int items = body == null ? 1 : ((Number) body.getOrDefault("items", 1)).intValue();
        String tier = body == null ? "standard" : String.valueOf(body.getOrDefault("tier", "standard"));

        OrderResult r = orders.createOrderWithTags(tier, items);

        if ("rejected".equals(r.status())) {
            return ResponseEntity.status(402).body(Map.of("error", "payment_declined"));
        }
        return ResponseEntity.status(201).body(r);
    }

    /** ⭐ a deliberately flaky endpoint, for testing alerts */
    @GetMapping("/flaky")
    public ResponseEntity<?> flaky() {
        int n = ThreadLocalRandom.current().nextInt(100);
        if (n < 20) {
            log.error("simulated internal error, n={}", n);
            return ResponseEntity.internalServerError().body(Map.of("error", "simulated"));
        }
        if (n < 30) {
            try { Thread.sleep(2500); } catch (InterruptedException ignored) {}
            return ResponseEntity.ok(Map.of("slow", true));
        }
        return ResponseEntity.ok(Map.of("ok", true));
    }

    @GetMapping("/health")
    public ResponseEntity<?> health() {
        return ResponseEntity.ok(Map.of("status", "UP"));
    }
}
```

```go
import (
	"log"

	"github.com/prometheus/client_golang/prometheus/promauto"

// ⭐ promauto registers with the default registry automatically.
var (
	// COUNTER
	checkoutsTotal = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "shop_checkouts_total",
		Help: "Total checkout attempts.",
	}, []string{"method", "status"}) // ⭐ bounded cardinality

	// HISTOGRAM with SLO-aligned buckets ⭐
	checkoutDuration = promauto.NewHistogramVec(prometheus.HistogramOpts{
		Name:    "shop_checkout_duration_seconds",
		Help:    "Checkout latency.",
		Buckets: []float64{.01, .025, .05, .1, .2, .3, .5, 1, 2, 5},
	}, []string{"method", "status"})

	// GAUGE
	inFlight = promauto.NewGauge(prometheus.GaugeOpts{
		Name: "shop_checkout_in_flight",
		Help: "Checkouts currently being processed.",
	})

	// DISTRIBUTION SUMMARY
	cartValue = promauto.NewHistogram(prometheus.HistogramOpts{
		Name:    "shop_cart_value_cents",
		Help:    "Cart value distribution.",
		Buckets: prometheus.ExponentialBuckets(100, 2, 12), // 100, 200, 400 … 204800
	})

	// a gauge from a function — evaluated at scrape time ⭐
	promauto.NewGaugeFunc(prometheus.GaugeOpts{
		Name: "shop_config_max_concurrency",
		Help: "The configured concurrency ceiling.",
	}, func() float64 { return 64 })
)

func main() {
	mux := http.NewServeMux()

	mux.HandleFunc("POST /checkout", func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		inFlight.Inc()
		defer inFlight.Dec()

		status := http.StatusCreated
		// simulate work
		time.Sleep(time.Duration(20+rand.Intn(280)) * time.Millisecond)
		if rand.Intn(100) < 5 {
			status = http.StatusBadGateway
		}

		value := 500 + rand.Intn(20000)
		cartValue.Observe(float64(value))

		// ⭐ observe duration with the SAME labels as the counter
		elapsed := time.Since(start).Seconds()
		st := strconv.Itoa(status)
		checkoutDuration.WithLabelValues(r.Method, st).Observe(elapsed)
		checkoutsTotal.WithLabelValues(r.Method, st).Inc()

		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(status)
		_, _ = w.Write([]byte(`{"status":"ok","value_cents":` + strconv.Itoa(value) +
			`,"duration_ms":` + strconv.Itoa(int(elapsed*1000)) + `}`))
	})

	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, _ *http.Request) {
		w.WriteHeader(http.StatusOK); _, _ = w.Write([]byte("ok"))
	})

	// ⭐ metrics on a SEPARATE mux → a separate port
	metricsMux := http.NewServeMux()
	metricsMux.Handle("/metrics", promhttp.HandlerFor(
		prometheus.DefaultGatherer,
		promhttp.HandlerOpts{
			EnableOpenMetrics:   true,  // ⭐ emits exemplars + _created timestamps
			Registry:            prometheus.DefaultRegisterer,
			ErrorHandling:       promhttp.ContinueOnError,
			DisableCompression:  false,
		},
	))
	metricsMux.HandleFunc("/healthz", func(w http.ResponseWriter, _ *http.Request) { w.WriteHeader(200) })

	go func() {
		log.Println("metrics on :9091")
		log.Fatal(http.ListenAndServe(":9091", metricsMux))
	}()

	log.Println("app on :8080")
	log.Fatal(http.ListenAndServe(":8080", mux))
}
```

```python
#!/usr/bin/env python3
"""A queue-consuming worker that exposes Prometheus metrics."""
import os, random, time, signal, sys, threading
from prometheus_client import (
    Counter, Gauge, Histogram, Info, Summary,
    start_http_server, REGISTRY,
)

# ── COUNTER ───────────────────────────────────────────────────
JOBS = Counter(
    "worker_jobs_processed_total",
    "Jobs processed",
    ["queue", "outcome"],                       # ⭐ bounded labels only
)

# ── HISTOGRAM with explicit buckets ⭐ ─────────────────────────
JOB_DURATION = Histogram(
    "worker_job_duration_seconds",
    "How long a job took",
    ["queue"],
    buckets=(0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10),
)

# ── GAUGE ─────────────────────────────────────────────────────
QUEUE_DEPTH = Gauge(
    "worker_queue_depth",
    "Messages waiting",
    ["queue"],
)
IN_FLIGHT = Gauge("worker_jobs_in_flight", "Jobs being processed right now")

# ── a gauge backed by a callback — evaluated at scrape time ───
def _memory_used_bytes() -> float:
    try:
        with open("/sys/fs/cgroup/memory.current") as f:      # cgroup v2
            return float(f.read().strip())
    except OSError:
        with open("/sys/fs/cgroup/memory/memory.usage_in_bytes") as f:
            return float(f.read().strip())

Gauge("worker_process_memory_bytes", "RSS from the cgroup", callback=_memory_used_bytes)

# ── INFO — a gauge with value 1 and informational labels ⭐ ───
Info("worker_build", "Build metadata")
REGISTRY.get_sample_value  # noqa
for r in REGISTRY.collect():
    pass
_info = None
for collector in REGISTRY._names_to_collectors.values():      # set it directly instead
    pass

# ── SUMMARY (usually you want a histogram instead) ────────────
BATCH = Summary("worker_batch_size", "Items per batch")

# ── lifecycle ─────────────────────────────────────────────────
SHUTDOWN = threading.Event()

def _sigterm(signum, frame):
    print("SIGTERM received, draining…", flush=True)
    SHUTDOWN.set()

signal.signal(signal.SIGTERM, _sigterm)
signal.signal(signal.SIGINT, _sigterm)


def main() -> None:
    port = int(os.environ.get("METRICS_PORT", "9092"))
    start_http_server(port)                       # ⭐ the Prometheus endpoint
    print(f"metrics on :{port}/metrics", flush=True)

    # set the build info gauge once
    for c in REGISTRY._names_to_collectors.values():
        pass
    REGISTRY.unregister(REGISTRY._names_to_collectors.get("worker_build_info"))  \
        if "worker_build_build_info" in REGISTRY._names_to_collectors else None

    while not SHUTDOWN.is_set():
        for queue in ("orders", "emails"):
            depth = random.randint(0, 250)
            QUEUE_DEPTH.labels(queue=queue).set(depth)

            while depth > 0 and not SHUTDOWN.is_set():
                batch = min(depth, random.randint(1, 20))
                BATCH.observe(batch)
                IN_FLIGHT.inc()
                start = time.perf_counter()
                outcome = "success"
                try:
                    time.sleep(random.uniform(0.01, 0.6))
                    if random.random() < 0.03:
                        raise RuntimeError("simulated failure")
                except Exception as exc:                       # noqa: BLE001
                    outcome = "error"
                    print(f"job failed: {exc}", flush=True)
                finally:
                    elapsed = time.perf_counter() - start
                    JOB_DURATION.labels(queue=queue).observe(elapsed)
                    JOBS.labels(queue=queue, outcome=outcome).inc()
                    IN_FLIGHT.dec()
                    depth -= batch

        SHUTDOWN.wait(timeout=5)

    print("shutdown complete", flush=True)


if __name__ == "__main__":
    main()
```

## 5. Step 5 — Recording rules

A **recording rule** pre-computes an expensive query into a new, cheap time series. You use them for three reasons:

1. **Performance** — a dashboard with 20 panels each running a 5-minute `rate()` over 400k series will melt your browser. A recording rule computes it once every 30s.
2. **Consistency** — every dashboard and alert uses *the same* definition of "error rate".
3. **Alerting** — multi-window burn-rate SLOs *require* recording rules (you can't put a 6h `rate()` in an alert evaluated every 30s without a huge cost).

**Naming convention: `level:metric:operations`**

```
job:http_requests:rate5m          ← per-job, an http_requests metric, a 5m rate
namespace_pod:container_cpu:sum
slo:sli_error:ratio_rate5m
instance:node_cpu_utilisation:rate5m
```

**`rules/shop-recording.yaml`**

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: shop-recording-rules
  namespace: monitoring
  labels: {release: kps, role: alert-rules}     # ⭐ so the ruleSelector picks it up
spec:
  groups:
    # ──────────────────────────────────────────────────────────
    - name: shop-red.rules
      interval: 30s
      rules:
        # ⭐ RATE — requests per second, per namespace+service+uri
        - record: job:http_server_requests:rate5m
          expr: |
            sum by (namespace, application, uri, method) (
              rate(http_server_requests_seconds_count{namespace="shop"}[5m])
            )

        # ⭐ ERRORS — the error ratio (4xx excluded; only 5xx count as OUR fault)
        - record: job:http_server_requests_errors:ratio_rate5m
          expr: |
            sum by (namespace, application) (
              rate(http_server_requests_seconds_count{namespace="shop",status=~"5.."}[5m])
            )
            /
            sum by (namespace, application) (
              rate(http_server_requests_seconds_count{namespace="shop"}[5m])
            )

        # ⭐ DURATION — p50 / p95 / p99
        - record: job:http_server_requests:p50_rate5m
          expr: |
            histogram_quantile(0.50,
              sum by (namespace, application, le) (
                rate(http_server_requests_seconds_bucket{namespace="shop"}[5m])))

        - record: job:http_server_requests:p95_rate5m
          expr: |
            histogram_quantile(0.95,
              sum by (namespace, application, le) (
                rate(http_server_requests_seconds_bucket{namespace="shop"}[5m])))

        - record: job:http_server_requests:p99_rate5m
          expr: |
            histogram_quantile(0.99,
              sum by (namespace, application, le) (
                rate(http_server_requests_seconds_bucket{namespace="shop"}[5m])))

        # ⭐ the EXACT SLO ratio (no interpolation error) — fraction faster than 300ms
        - record: job:http_server_requests_latency_good:ratio_rate5m
          expr: |
            sum by (namespace, application) (
              rate(http_server_requests_seconds_bucket{namespace="shop",le="0.3"}[5m]))
            /
            sum by (namespace, application) (
              rate(http_server_requests_seconds_count{namespace="shop"}[5m]))

        # per-URI top errors
        - record: job:http_server_requests_errors_by_uri:rate5m
          expr: |
            sum by (namespace, application, uri) (
              rate(http_server_requests_seconds_count{namespace="shop",status=~"5.."}[5m]))

    # ──────────────────────────────────────────────────────────
    - name: shop-saturation.rules
      interval: 30s
      rules:
        # ⭐ CPU throttling ratio — the hidden latency killer
        - record: namespace_pod:container_cpu_throttling:ratio_rate5m
          expr: |
            sum by (namespace, pod) (rate(container_cpu_cfs_throttled_periods_total{namespace="shop"}[5m]))
            /
            sum by (namespace, pod) (rate(container_cpu_cfs_periods_total{namespace="shop"}[5m]))

        # memory as a fraction of the limit
        - record: namespace_pod:container_memory_utilisation:ratio
          expr: |
            sum by (namespace, pod, container) (container_memory_working_set_bytes{namespace="shop"})
            /
            sum by (namespace, pod, container) (
              kube_pod_container_resource_limits{namespace="shop",resource="memory"})

        # Tomcat thread-pool saturation ⭐ (a leading indicator)
        - record: application:tomcat_threads_busy:ratio
          expr: |
            sum by (application) (tomcat_threads_busy_threads)
            /
            sum by (application) (tomcat_threads_config_max_threads)

        # Hikari connection-pool saturation ⭐
        - record: application:hikari_connections_active:ratio
          expr: |
            sum by (application) (hikaricp_connections_active)
            /
            sum by (application) (hikaricp_connections_max)

        - record: application:hikari_connections_pending:sum
          expr: sum by (application) (hikariicp_connections_pending)   # note: see the fix below

    # ──────────────────────────────────────────────────────────
    - name: shop-business.rules
      interval: 30s
      rules:
        - record: application:shop_orders_created:rate5m
          expr: sum by (application, channel) (rate(shop_orders_created_total[5m]))
        - record: application:shop_orders_rejected:ratio_rate5m
          expr: |
            sum by (application) (rate(shop_orders_rejected_total[5m]))
            /
            (sum by (application) (rate(shop_orders_created_total[5m]))
             + sum by (application) (rate(shop_orders_rejected_total[5m])))
        - record: application:shop_order_processing:p99_rate5m
          expr: |
            histogram_quantile(0.99,
              sum by (application, le) (rate(shop_order_processing_duration_seconds_bucket[5m])))
        - record: application:shop_checkout:p99_rate5m
          expr: |
            histogram_quantile(0.99,
              sum by (le) (rate(shop_checkout_duration_seconds_bucket[5m])))
```

```yaml
spec:
```

The essential panels and their queries:

| Panel | Type | Query |
|---|---|---|
| **Availability (30d)** | Stat, gauge | `1 - (sum(increase(http_server_requests_seconds_count{application="shop-api",status=~"5.."}[30d])) / sum(increase(http_server_requests_seconds_count{application="shop-api"}[30d])))` |
| **Error budget remaining** | Stat | `100 * (1 - (sum(increase(http_server_requests_seconds_count{application="shop-api",status=~"5.."}[30d])) / (0.001 * sum(increase(http_server_requests_seconds_count{application="shop-api"}[30d])))))` |
| **Burn rate (5m)** | Stat, thresholds 1/6/14.4 | `sum(rate(http_server_requests_seconds_count{application="shop-api",status=~"5.."}[5m])) / (0.001 * sum(rate(http_server_requests_seconds_count{application="shop-api"}[5m])))` |
| **Request rate** | Time series | `sum(rate(http_server_requests_seconds_count{application="shop-api"}[$__rate_interval]))` |
| **Request rate by URI** | Time series | `sum by (uri) (rate(http_server_requests_seconds_count{application="shop-api"}[$__rate_interval]))` |
| **Error rate** | Time series, red | `job:http_server_requests_errors:ratio_rate5m{application="shop-api"}` |
| **Errors by status** | Time series, stacked | `sum by (status) (rate(http_server_requests_seconds_count{application="shop-api",status=~"[45].."}[$__rate_interval]))` |
| **Latency percentiles** | Time series, 3 queries | `job:http_server_requests:p50_rate5m{…}`, `…p95…`, `…p99…` |
| ⭐ **Latency heatmap** | Heatmap | `sum(increase(http_server_requests_seconds_bucket{application="shop-api"}[$__rate_interval])) by (le)` — Format: **Heatmap**, `le` as the bucket |
| **p99 by URI** | Table | `topk(10, histogram_quantile(0.99, sum by (uri, le) (rate(http_server_requests_seconds_bucket{application="shop-api"}[$__rate_interval]))))` |

## 9. Step 9 — A real SLO with sloth

Writing multi-window burn-rate rules by hand is error-prone. [sloth](https://sloth.dev) generates them.

## 10. Step 10 — HPA on a custom metric

`prometheus-adapter` exposes Prometheus metrics through the `custom.metrics.k8s.io` API so an HPA can scale on **business load** rather than CPU.

```bash
# is the adapter serving?
kubectl get apiservices | grep custom.metrics
# v1beta1.custom.metrics.k8s.io   monitoring/kps-prometheus-adapter   True   10m

# what metrics are available?
kubectl get --raw "/apis/custom.metrics.k8s.io/v1beta1" | jq -r '.resources[].name' | head -20
# namespaces/requests_per_second
# pods/requests_per_second

# query one
kubectl get --raw "/apis/custom.metrics.k8s.io/v1beta1/namespaces/shop/pods/*/requests_per_second" | jq .
# {"kind":"MetricValueList","items":[
#   {"describedObject":{"kind":"Pod","name":"shop-api-7d4f8c9b6-abcde"},
#    "metricName":"requests_per_second","value":"42"}]}
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: shop-api-rps, namespace: shop}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: shop-api}
  minReplicas: 3
  maxReplicas: 15
  metrics:
    # ⭐ the custom metric — scale on requests per second per pod
    - type: Pods
      pods:
        metric: {name: requests_per_second}
        target: {type: AverageValue, averageValue: "50"}
    # keep CPU as a safety net
    - type: Resource
      resource: {name: cpu, target: {type: Utilization, averageUtilization: 80}}
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - {type: Percent, value: 100, periodSeconds: 15}
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - {type: Percent, value: 10, periodSeconds: 60}
```

```bash
kubectl delete hpa shop-api -n shop                       # remove the CPU-only one
kubectl apply -f - <<'EOF'
# (the YAML above)
EOF

kubectl get hpa -n shop -w
# NAME            REFERENCE             TARGETS       MINPODS  MAXPODS  REPLICAS  AGE
# shop-api-rps    Deployment/shop-api   12/50 (avg)   3        15       3         30s

# ⭐ drive load and watch it scale
kubectl run hammer --image=curlimages/curl:8.10.1 -n shop --restart=Never --command -- \
  sh -c 'while true; do for i in $(seq 1 100); do curl -s -o /dev/null http://shop-api/api/items & done; wait; done'
kubectl get hpa -n shop; kubectl get pods -n shop -l app=shop-api
kubectl describe hpa shop-api-rps -n shop | tail -15
# Events:
#   Normal  SuccessfulRescale  2m  horizontal-pod-autoscaler  New size: 6; reason: pods metric requests_per_second above target
kubectl delete pod hammer -n shop
```

> 🔑 **Scaling on RPS beats scaling on CPU for I/O-bound services.** A Spring Boot app waiting on a slow database has *low* CPU and *high* latency — a CPU-based HPA won't scale, and your users suffer. RPS (or queue depth, or concurrency) scales on actual demand.

## 12. Step 12 — Break it on purpose (the most valuable hour)

Learning a monitoring stack means watching it fail. Do each of these and observe.

### 12.1 Kill the app → watch the whole alert chain

```bash
# terminal 1: watch the alert pipeline
kubectl logs -n monitoring deploy/alert-echo -f &

# terminal 2: watch Prometheus's view
watch -n2 "curl -s localhost:9090/api/v1/alerts | jq -r '.data.alerts[] | \"\(.state)\t\(.labels.alertname)\"' | sort"

# terminal 3: break it
kubectl scale deploy/shop-api -n shop --replicas=0
```

What you should see, in order:

```
t+0s     kube_deployment_status_replicas_available → 0
t+15s    the next Prometheus evaluation
t+15s    ShopApiNoReadyReplicas      → PENDING  (for: 1m)
t+30s    up{namespace="shop"}        → 0 (no targets, so actually the series goes stale)
t+45s    ShopApiNoReadyReplicas      → FIRING   → Alertmanager
t+75s    group_wait: 30s elapses     → the webhook receives it
         📨 ALERT NOTIFICATION  status=firing  group={"alertname":"ShopApiNoReadyReplicas"}
t+2m     ShopApiTargetDown           → FIRING
t+2m     ShopApiHighErrorRate        → no data (there's no traffic) — ⭐ note this!
```

> 🔑 **A subtle and important lesson: `ShopApiHighErrorRate` does NOT fire when the service is fully down**, because there are no requests at all — and `0/0` is not `> 0.01`. This is why you need a **separate availability alert** (`up == 0`, or `replicas_available == 0`). An error-rate alert alone gives you a silent total outage.

```bash
# recover
kubectl scale deploy/shop-api -n shop --replicas=3
kubectl rollout status deploy/shop-api -n shop
# → the alerts resolve, and you see status=resolved in the webhook (send_resolved: true)
```

## 13. Step 13 — Long-term storage (the graduation step)

Prometheus's local TSDB is not designed for months of data or a global view. When you outgrow it:

| Need | Solution |
|---|---|
| Keep 13 months for compliance | **Thanos** (sidecar + object storage) or **Mimir** |
| Query 50 clusters as one | Thanos Query / Mimir / VictoriaMetrics cluster |
| Cut storage cost 10× | Downsampling to 5m and 1h resolutions |
| Deduplicate HA replicas | Thanos/Mimir `replica` label handling |
| A drop-in replacement with less ops | **VictoriaMetrics** (PromQL-compatible, single binary) |

```yaml
# Thanos sidecar, via the kube-prometheus-stack values
prometheus:
  thanosService:
    enabled: true
  thanosServiceMonitor:
    enabled: true
  prometheusSpec:
    thanos:
      image: quay.io/thanos/thanos:v0.37.2
      version: v0.37.2
      objectStorageConfig:
        name: thanos-objstore
        key: objstore.yml
      # ⭐ the sidecar uploads 2-hour blocks to S3
```

```yaml
# the objstore secret
apiVersion: v1
kind: Secret
```

### Task 1.1 — Instrument a brand-new service and get it on a dashboard

Add a fourth service, `inventory-api`, written in **Go**, exposing three metrics:
- `shop_inventory_lookups_total{sku_status="hit|miss"}` — a counter
- `shop_inventory_lookup_duration_seconds` — a histogram with buckets `0.001, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25`
- `shop_inventory_cache_entries` — a gauge

Requirements: metrics on port **9093** (separate from the app port 8080), scraped by Prometheus via a **ServiceMonitor**, and a Grafana panel showing the **cache hit ratio** and the **p95 lookup latency**.

<details>
<summary><b>💡 Hint</b></summary>

The cache hit ratio is `rate(hits) / (rate(hits) + rate(misses))` — not `rate(hits) / rate(lookups_total)` unless you have a single total counter. And `histogram_quantile` needs `by (le)`.
</details>

**✅ Answer**

```go
package main

import (
	"log"; "math/rand"; "net/http"; "strconv"; "sync/atomic"; "time"
	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promauto"
	"github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
	lookups = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "shop_inventory_lookups_total",
		Help: "Cache lookups by outcome.",
	}, []string{"sku_status"})          // ⭐ bounded: only "hit" or "miss"

	lookupDur = promauto.NewHistogram(prometheus.HistogramOpts{
		Name:    "shop_inventory_lookup_duration_seconds",
		Help:    "Cache lookup latency.",
		Buckets: []float64{.001, .005, .01, .025, .05, .1, .25},   // ⭐ sub-100ms service
	})

	entries atomic.Int64
)

func init() {
	promauto.NewGaugeFunc(prometheus.GaugeOpts{
		Name: "shop_inventory_cache_entries",
		Help: "Items currently in the inventory cache.",
	}, func() float64 { return float64(entries.Load()) })
}

func main() {
	entries.Store(1200)

	mux := http.NewServeMux()
	mux.HandleFunc("GET /inventory/{sku}", func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		hit := rand.Intn(100) < 82                 // 82% hit rate
		status := "miss"
		if hit {
			status = "hit"
		} else {
			time.Sleep(time.Duration(20+rand.Intn(80)) * time.Millisecond)  // a miss hits the DB
			entries.Add(1)
		}
		lookupDur.Observe(time.Since(start).Seconds())
		lookups.WithLabelValues(status).Inc()
		w.Header().Set("Content-Type", "application/json")
		_, _ = w.Write([]byte(`{"sku":"` + r.PathValue("sku") + `","hit":` + strconv.FormatBool(hit) + `}`))
	})
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, _ *http.Request) { w.WriteHeader(200) })

	metricsMux := http.NewServeMux()
	metricsMux.Handle("/metrics", promhttp.Handler())          // ⭐ port 9093 only
	metricsMux.HandleFunc("/healthz", func(w http.ResponseWriter, _ *http.Request) { w.WriteHeader(200) })

	go func() { log.Println("metrics :9093"); log.Fatal(http.ListenAndServe(":9093", metricsMux)) }()
	log.Println("app :8080"); log.Fatal(http.ListenAndServe(":8080", mux))
}
```

### Task 1.2 — An alert that must NOT fire on a deploy

Every deploy causes a brief spike in 5xx errors as old pods terminate and new ones warm up. Your `ShopApiHighErrorRate` alert fires on every release, and the team has started ignoring it.

**Fix it three different ways**, and explain the trade-off of each.

**✅ Answer**

**Way 1 — lengthen `for:`.** The simplest, and often enough.

```yaml
- alert: ShopApiHighErrorRate
  expr: job:http_server_requests_errors:ratio_rate5m{application="shop-api"} > 0.01
  for: 10m                       # was 5m
```

A rollout with `maxUnavailable: 0` and `minReadySeconds: 15` completes in ~90s for 3 replicas. A 10-minute `for:` means a deploy blip never reaches FIRING. **Trade-off:** a real outage now takes 10 minutes to page. For a Tier-1 service that's too slow.

**Way 2 — silence it automatically during deploys.** The right answer.

```bash
# in the deploy pipeline, immediately before `kubectl apply`:
SIL_ID=$(curl -s -XPOST http://alertmanager:9093/api/v2/silences \
  -H 'Content-Type: application/json' -d '{
    "matchers":[
      {"name":"namespace","value":"shop","isRegex":false,"isEqual":true},
      {"name":"alertname","value":"ShopApiHighErrorRate","isRegex":false,"isEqual":true}
    ],
    "startsAt": "'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'",
    "endsAt":   "'"$(date -u -d '+10 minutes' +%Y-%m-%dT%H:%M:%SZ)"'",
    "createdBy": "ci-pipeline",
    "comment":   "Automated silence for release '"$GIT_SHA"'"
  }' | jq -r .silenceID)

kubectl apply -f ./k8s/ -R
kubectl rollout status deploy/shop-api -n shop --timeout=300s

# expire it as soon as the rollout is verified — don't wait for the timer
curl -s -XDELETE "http://alertmanager:9093/api/v2/silence/$SIL_ID"
```

**Trade-off:** you must be disciplined about expiring the silence, and a genuine outage *during* the window is hidden. Mitigate by keeping the window short (10 min) and by keeping the SLO burn-rate alert **un-silenced** — a fast burn is a real problem even during a deploy.

**Way 3 — make the alert itself deploy-aware.** The most elegant, and the one that shows senior thinking.

```yaml
# a recording rule that reports "is a rollout in progress?"
- record: application:rollout_in_progress:bool
  expr: |
    max by (namespace, deployment) (
      kube_deployment_status_replicas_updated{namespace="shop"}
        != kube_deployment_spec_replicas{namespace="shop"}
    ) or vector(0)
```

```yaml
- alert: ShopApiHighErrorRate
  expr: |
    job:http_server_requests_errors:ratio_rate5m{application="shop-api"} > 0.01
    unless on(namespace)
    application:rollout_in_progress:bool{namespace="shop"} == 1
  for: 5m
```

**Trade-off:** `unless` suppresses the alert for the whole rollout, so a genuinely broken release won't page until the rollout either completes or stalls. Combine it with a `progressDeadlineSeconds` alert (`kube_deployment_status_condition{condition="Progressing",status="false"}`) so a stuck rollout is caught by a *different* alert.

**Way 4 (the real fix) — eliminate the blip.** All three above are mitigations; the root cause is that the deploy drops requests. Fix that instead:

```yaml
spec:
  strategy: {rollingUpdate: {maxSurge: 1, maxUnavailable: 0}}   # never remove a ready pod early
  minReadySeconds: 15                                            # let it warm up
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - lifecycle:
            preStop: {exec: {command: ["sh","-c","sleep 10"]}}   # ⭐ let endpoints propagate
          readinessProbe:
            httpGet: {path: /health/readiness, port: 9090}
            initialDelaySeconds: 0
            periodSeconds: 5
            failureThreshold: 2
```

With `preStop: sleep 10` and `maxUnavailable: 0`, the deploy produces **zero** 5xx — and then you don't need any of the first three mitigations. **Do this first.** Use a silence (Way 2) as the belt-and-braces.

### Task 1.4 — Find the latency problem in a trace-less world

Latency on `POST /api/orders` jumped from 180ms p99 to 2.4s p99 at 15:10. Error rate is **0%**. CPU utilization is 45%. You have no tracing yet (that's Case 2). Find the cause using only Prometheus + Grafana, in under 10 minutes.

**✅ Answer — the exact order to check things**

```promql
# 1. Is it ALL pods or ONE? (a bad pod vs a systemic problem)
histogram_quantile(0.99,
  sum by (pod, le) (rate(http_server_requests_seconds_bucket{uri="/api/orders"}[$__rate_interval])))
# → all 3 pods are equally slow ⇒ systemic. If one pod: kubectl delete pod, done.

# 2. Is it ALL endpoints or just this one?
histogram_quantile(0.99,
  sum by (uri, le) (rate(http_server_requests_seconds_bucket[$__rate_interval])))
# → only /api/orders ⇒ the problem is downstream of that handler.

# 3. ⭐ Is it OUR code or a DEPENDENCY? Check saturation of every pool first.
application:hikari_connections_active:ratio            # DB pool
# → 1.0  ⛔ THE POOL IS FULL
application:hikari_connections_pending:sum
# → 12   ⛔ 12 threads WAITING for a connection

# 4. Confirm with Tomcat
application:tomcat_threads_busy:ratio
# → 0.94  ⛔ threads are piling up because they're blocked on the pool

# 5. Where is the time going? Break the request into phases.
histogram_quantile(0.99, sum by (le) (rate(hikaricp_connections_acquire_seconds_bucket[$__rate_interval])))
# → 1.8s  ⭐ acquiring a connection takes 1.8 seconds. That's the latency.

# 6. Why is the pool exhausted? Is the DB slow, or is there a leak?
# If you have a postgres_exporter:
rate(pg_stat_database_xact_commit{datname="shop"}[$__rate_interval])       # throughput
pg_stat_activity_count{state="active"}                                      # active queries
histogram_quantile(0.99, sum by (le) (rate(pg_stat_statements_mean_time_seconds_bucket[$__rate_interval])))
# → DB queries are fast (2ms). So it's NOT the database being slow.

# 7. ⭐ Therefore: a CONNECTION LEAK, or a request holding connections too long.
hikaricp_connections_active        # stuck at max, never released
hikaricp_connections_idle          # 0
increase(hikaricp_connections_timeout_total[10m])   # 34  ⛔ threads timed out waiting

# 8. Did something change at 15:10?
changes(kube_deployment_created{namespace="shop"}[1h])
kube_deployment_status_replicas_updated{deployment="shop-api"} != kube_deployment_spec_replicas{deployment="shop-api"}
# → a rollout happened at 15:08  ⭐ THE DEPLOY IS THE CAUSE

# 9. Confirm the GC isn't it (rule out the other usual suspect)
rate(jvm_gc_pause_seconds_sum{application="shop-api"}[$__rate_interval])
  / rate(jvm_gc_pause_seconds_count{application="shop-api"}[$__rate_interval])
# → 8ms. Not GC.

# 10. Rule out CPU throttling
namespace_pod:container_cpu_throttling:ratio{namespace="shop"}
# → 0.01. Not throttling.
```

**Conclusion:** the 15:08 deploy introduced a connection leak — connections are acquired and never returned, so `hikaricp_connections_active` is pinned at `max`, new requests wait ~1.8s for a connection (then time out), and Tomcat threads pile up. Latency rises with **zero errors** because the requests eventually succeed.

**Mitigate:** `kubectl rollout undo deploy/shop-api -n shop`.
**Confirm the diagnosis:** after the rollback, `hikaricp_connections_active` drops below max within a minute and p99 returns to 180ms.

**The general principle this task teaches:**

```
Latency up + errors flat  ⇒  SATURATION, not failure.
The order to check saturation:
  1. per-pod vs all pods          (a bad instance?)
  2. per-endpoint vs all          (a bad route?)
  3. every POOL: DB, thread, HTTP client, cache    ← ⭐ usually the answer
  4. GC pause time                (a JVM thing)
  5. CPU throttling               (a Kubernetes thing)
  6. disk I/O saturation          (node_disk_io_time_seconds_total)
  7. DNS latency                  (coredns_dns_request_duration_seconds)
  8. network retransmits          (node_netstat_Tcp_RetransSegs)
  9. what changed? deploys, config, traffic
```

### Task 1.5 — Put the whole monitoring config in CI

Nothing in `rules/` or `dashboards/` may reach the cluster without passing validation. Build a pipeline that:
1. Lints every `PrometheusRule` with `promtool check rules`
2. Runs the PromQL **unit tests** with `promtool test rules`
3. Validates the Alertmanager config with `amtool check-config`
4. Validates every dashboard JSON parses and has no orphan datasource UIDs
5. Dry-run-applies everything against the live cluster
6. Fails the build on any of the above

**✅ Answer** — `.github/workflows/observability-ci.yaml`:

```yaml
name: observability-ci
on:
  pull_request:
    paths: ['rules/**', 'dashboards/**', 'manifests/**', 'slo.yaml']
  push:
    branches: [main]

env:
  PROM_VERSION: v3.13.2
  AM_VERSION: v0.28.1

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # ── 1 & 2: promtool, from the official image (no install needed) ──
      - name: Extract raw rules from the PrometheusRule CRDs
        run: |
          mkdir -p /tmp/raw
          for f in rules/*.yaml; do
            n=$(basename "$f" .yaml)
            # a PrometheusRule has spec.groups; promtool wants a top-level `groups:`
            yq '.spec.groups as $g | {"groups": $g}' "$f" > "/tmp/raw/$n.yaml"
            echo "extracted $n"
          done

      - name: promtool check rules
        run: |
          fail=0
          for f in /tmp/raw/*.yaml; do
            echo "── checking $f"
            docker run --rm -v /tmp/raw:/rules quay.io/prometheus/prometheus:${PROM_VERSION} \
              promtool check rules "/rules/$(basename $f)" || fail=1
          done
          [ $fail -eq 0 ] || { echo "::error::rule validation failed"; exit 1; }

      - name: promtool check config (the whole prometheus.yml if present)
        run: |
          [ -f prometheus.yml ] && docker run --rm -v "$PWD":/w -w /w \
            quay.io/prometheus/prometheus:${PROM_VERSION} promtool check config prometheus.yml || echo "no prometheus.yml, skipped"

      - name: ⭐ promtool test rules (PromQL unit tests)
        run: |
          [ -d tests ] || { echo "no tests/ dir"; exit 0; }
          docker run --rm -v "$PWD/tests:/tests" -v /tmp/raw:/raw \
            quay.io/prometheus/prometheus:${PROM_VERSION} \
            promtool test rules /tests/*_test.yaml

      - name: sloth generate + validate (if slo.yaml exists)
        run: |
          [ -f slo.yaml ] || exit 0
          docker run --rm -v "$PWD":/w -w /w slothdev/sloth:v0.13.0 generate -i slo.yaml -o /tmp/slo-generated.yaml
          docker run --rm -v /tmp:/tmp quay.io/prometheus/prometheus:${PROM_VERSION} \
            promtool check rules /tmp/slo-generated.yaml
          # ⭐ fail if the committed generated file is stale
          git diff --no-index --exit-code slo-generated.yaml /tmp/slo-generated.yaml \
            || { echo "::error::slo-generated.yaml is out of date — re-run sloth generate"; exit 1; }

      # ── 3: amtool ─────────────────────────────────────────────
      - name: Extract and validate the Alertmanager config
        run: |
          yq '.alertmanager.config' kps-values.yaml > /tmp/alertmanager.yml
          docker run --rm -v /tmp:/etc/alertmanager quay.io/prometheus/alertmanager:${AM_VERSION} \
            amtool check-config /etc/alertmanager/alertmanager.yml
          # ⭐ also assert the things humans forget
          grep -q 'inhibit_rules' /tmp/alertmanager.yml || { echo "::error::no inhibit_rules"; exit 1; }
          grep -q 'repeat_interval' /tmp/alertmanager.yml || { echo "::error::no repeat_interval"; exit 1; }

      # ── 4: dashboards ────────────────────────────────────────
      - name: Validate dashboard JSON
        run: |
          fail=0
          for f in dashboards/*.json; do
            jq empty "$f" || { echo "::error::$f is not valid JSON"; fail=1; continue; }
            # ⭐ every datasource uid must be one we know about
            bad=$(jq -r '[.. | objects | select(has("datasource")) | .datasource
                          | if type=="object" then .uid else . end] | .[]' "$f" 2>/dev/null \
                  | sort -u | grep -vE '^(prometheus|loki|tempo|Prometheus|-- Grafana --)$' || true)
            [ -n "$bad" ] && { echo "::error::$f references unknown datasource uid(s): $bad"; fail=1; }
            # ⭐ no hardcoded rate windows — Grafana best practice
            grep -o '\$__interval' "$f" | head -1 >/dev/null || \
              echo "::warning::$f does not use \$__interval / \$__rate_interval"
            # ⭐ every panel must have a title
            jq -e '.panels[] | select(.type!="row") | select((.title // "")=="")' "$f" >/dev/null 2>&1 \
              && { echo "::error::$f has an untitled panel"; fail=1; }
            echo "✅ $f"
          done
          [ $fail -eq 0 ]

      - name: Every alert must have a runbook_url ⭐
        run: |
          missing=$(yq -r '.spec.groups[].rules[] | select(.alert) | select(.annotations.runbook_url == null) | .alert' rules/*.yaml || true)
          [ -z "$missing" ] || { echo "::error::alerts missing runbook_url:"; echo "$missing"; exit 1; }

      - name: Every alert must have severity and team
        run: |
          bad=$(yq -r '.spec.groups[].rules[] | select(.alert) |
                 select(.labels.severity == null or .labels.team == null) | .alert' rules/*.yaml || true)
          [ -z "$bad" ] || { echo "::error::alerts missing severity/team:"; echo "$bad"; exit 1; }

      - name: severity must be critical or warning only
        run: |
          bad=$(yq -r '.spec.groups[].rules[] | select(.alert) | .labels.severity' rules/*.yaml \
                | sort -u | grep -vE '^(critical|warning)$' || true)
          [ -z "$bad" ] || { echo "::error::unknown severity values: $bad"; exit 1; }

      - name: No alert may be missing `for:`
        run: |
          bad=$(yq -r '.spec.groups[].rules[] | select(.alert) | select(.for == null) | .alert' rules/*.yaml || true)
          [ -z "$bad" ] || { echo "::warning::alerts without for: (will fire on a single sample): $bad"; }

  deploy-check:
    needs: validate
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    steps:
      - uses: actions/checkout@v4
      # ── 5: a real dry-run against a throwaway cluster ────────
      - uses: helm/kind-action@v1
        with: {cluster_name: ci}
      - run: |
          helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
          helm install kps prometheus-community/kube-prometheus-stack \
            -n monitoring --create-namespace -f kps-values.yaml --wait --timeout 10m
          # ⭐ the real test: does the cluster ACCEPT these rules?
          kubectl apply -f rules/ --dry-run=server
          kubectl apply -f manifests/ --dry-run=server
          kubectl apply -f rules/
          sleep 30
          # and did they actually load and evaluate cleanly?
          kubectl port-forward -n monitoring svc/kps-kube-prometheus-stack-prometheus 9090:9090 &
          sleep 10
          unhealthy=$(curl -s localhost:9090/api/v1/rules | jq -r '[.data.groups[].rules[] | select(.health!="ok")] | length')
          [ "$unhealthy" = "0" ] || { echo "::error::$unhealthy rules failed to evaluate"; \
            curl -s localhost:9090/api/v1/rules | jq '.data.groups[].rules[] | select(.health!="ok")'; exit 1; }
          echo "✅ all rules loaded and healthy"
```

**Why each step exists:**

| Step | The failure it catches |
|---|---|
| `promtool check rules` | A YAML/PromQL syntax error — the rule group silently doesn't load |
| `promtool test rules` | ⭐ An alert that fires when it shouldn't, or doesn't fire when it should |
| Stale `slo-generated.yaml` | Someone edited `slo.yaml` and forgot to regenerate |
| `amtool check-config` | A routing tree that sends everything to `null`, or a typo'd receiver |
| No `inhibit_rules` | 200 alerts for one node failure |
| Dashboard JSON validation | A broken dashboard silently replaces a working one |
| Unknown datasource UID | ⭐ A dashboard imported from grafana.com that queries a datasource you don't have → "No data" everywhere |
| Missing `runbook_url` | The 3am responder has no idea what to do |
| `severity` values | A typo (`critcal`) that routes the alert to the default receiver |
| `--dry-run=server` | A quota, webhook, PSA or RBAC rejection |
| The `health != "ok"` check | ⭐⭐ A rule that **loads** but fails to **evaluate** — e.g. it references a recording rule that doesn't exist yet |
