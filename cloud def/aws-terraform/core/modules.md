# Terraform Modules (AWS) — Interview Questions

> **Cloud:** AWS · **IaC Tool:** Terraform · **Levels:** Case A (Basic) · Case B (Advanced/Senior) · Case C (Scenario) · **Reading time:** ~6 min

---

## Case A — Basic

**A1. What is a Terraform module?**
**Answer:** A container for a group of related resources, defined as a directory of `.tf` files. The root module is your main working directory; child modules are called from it.

**A2. What is the root module?**
**Answer:** The working directory where you run `terraform` — every config has one. It can call child modules and define its own resources.

**A3. How do you call a child module?**
**Answer:** With a `module` block: `module "vpc" { source = "./modules/vpc" ; cidr = "10.0.0.0/16" }`. `source` points to a local path, registry, or Git repo.

**A4. What does the `source` argument accept?**
**Answer:** Local paths (`./modules/vpc`), the public Terraform Registry (`terraform-aws-modules/vpc/aws`), private registries, Git URLs (with `ref`), and HTTP/S URLs for archives.

**A5. How do modules communicate values?**
**Answer:** Inputs go in via module arguments (matched to the module's variables); outputs come back via the module's `output` blocks, referenced as `module.vpc.vpc_id`.

**A6. What is the public Terraform Registry?**
**Answer:** A catalog of community and vendor modules/providers. AWS modules like `terraform-aws-modules/vpc/aws` are widely used starting points.

**A7. How do you pin a registry module version?**
**Answer:** `source = "terraform-aws-modules/vpc/aws" ; version = "5.0.0"` (or a constraint like `~> 5.0`).

**A8. What files conventionally belong in a module directory?**
**Answer:** `main.tf`, `variables.tf`, `outputs.tf`, optionally `versions.tf` (required_providers) and `README.md`.

**A9. What is module composition?**
**Answer:** Building larger systems by nesting modules — e.g. a `network` module used inside an `app` module — each with clean input/output contracts.

**A10. Can a module contain another module?**
**Answer:** Yes — modules can call other modules, forming a tree. Depth is only limited by complexity; keep it reasonable.

**A11. What is a module's `providers` argument?**
**Answer:** It lets you pass alternate provider configurations (e.g. an aliased provider or one pinned to another region) into a module: `providers = { aws = aws.west }`.

**A12. How do you document a module?**
**Answer:** With a README covering purpose, inputs/outputs tables (often generated by `terraform-docs`), usage examples, and versioning.

**A13. What is the difference between a module and a workspace?**
**Answer:** A module packages reusable config; a workspace is a separate instance of state for the same config (environment isolation). They solve different problems.

**A14. How do you update a module to a new version?**
**Answer:** Change the `version` constraint and run `terraform init -upgrade`, then `plan` to review the diff before applying.

**A15. Can you use `count`/`for_each` on a module block?**
**Answer:** Yes — module blocks support both, letting you instantiate a module multiple times with different inputs, e.g. one VPC per environment.

## Case B — Advanced / Senior

**B1. How do you design a good module API?**
**Answer:** Small surface of well-typed inputs with defaults, meaningful outputs, no hidden dependencies on caller resources, clear naming, and versioning. Treat the module like a library: document and test it.

**B2. What is the recommended structure for a large reusable module?**
**Answer:** Nested submodules for distinct concerns (e.g. `modules/vpc`, `modules/subnets`) exposed by a thin root wrapper with `count = 0/1` enable flags, so consumers can compose pieces without reimplementing them.

**B3. Why pass providers explicitly into modules?**
**Answer:** So a module uses the caller's provider config (region, assume-role) and, with `providers = {...}`, specific aliases. Without it, modules use the default provider of the caller — which can surprise in multi-region setups.

**B4. How do `count`/`for_each` on modules change output references?**
**Answer:** Outputs become collections: `module.vpc[0].id` or `module.app["blue"].url`. Consumers must index them; keep keys stable to avoid churn.

**B5. What is the "enable flag" pattern?**
**Answer:** Wrapping optional resources in `count = var.enable_x ? 1 : 0` so consumers can toggle features. It keeps one module instead of many variants, though it can bloat the code.

**B6. How do you version modules stored in Git?**
**Answer:** Use Git tags and reference them: `source = "git::https://github.com/org/repo.git?ref=v1.2.0"`. Pinning to a tag (not a branch) gives reproducible builds.

**B7. What is the risk of a module reaching out to the network (remote-exec, external data source)?**
**Answer:** It creates hidden, non-idempotent side effects outside Terraform's graph and can fail unpredictably. Prefer provider-native resources; if unavoidable, document and gate it.

**B8. How do you test a module?**
**Answer:** With example root modules run in CI (plan/apply/destroy against sandbox accounts), plus tools like Terratest for Go-based assertions, `terraform validate`, and linting with `tflint`.

**B9. Explain module registry "verified" and version constraints.**
**Answer:** The registry supports `~>`, `>=`, exact pins. Verified modules come from trusted publishers. Use constraints that balance stability (`~> 5.0`) with getting patches.

**B10. How do you refactor repeated inline resources into a module without downtime?**
**Answer:** Create the module, move each resource into it with `moved` blocks (or `terraform state mv`), run plan to confirm "no changes", then delete the old inline definitions.

**B11. What are the downsides of overly deep module nesting?**
**Answer:** Harder to trace where a value comes from, more outputs to thread through each layer, slower reviews, and confusion over provider config. Favor shallow, well-named composition.

**B12. How do modules handle secrets?**
**Answer:** Inputs marked `sensitive` propagate sensitivity through outputs. Never hardcode secrets in a module; pass them in and ensure the module doesn't echo them into logs or non-sensitive outputs.

## Case C — Scenario

**C1. You have five nearly identical app stacks. How do you DRY them up?**
**Answer:** Build one parameterized `app-stack` module (network + compute + data) with per-stack inputs, instantiate it with `for_each` over a map of stacks, and keep environment-specific values in tfvars. Avoid copying directories.

**C2. A community module you depend on introduced a breaking change. How do you respond?**
**Answer:** Pin the last working version, review the changelog, adapt your inputs or wrap it with your own module as an adapter, then test the upgrade in a sandbox before bumping the constraint.

**C3. You need the same VPC module in two regions with different CIDRs.**
**Answer:** Call the module twice with different inputs and `providers = { aws = aws.us_east_1 }` / `{ aws = aws.eu_west_1 }` using aliased providers, so each instance targets its region.

**C4. A consumer keeps breaking a shared module because they don't understand an input.**
**Answer:** Add validation blocks with clear error messages, improve the README/examples, expose only what's needed (shrink the API), and version the module so changes are opt-in.

**C5. Management wants to reuse your internal module without publishing to the public registry.**
**Answer:** Host a private registry (Terraform Cloud/Enterprise or GitLab), or reference the module by Git tag over SSH. Document install and versioning so teams pin versions.

**C6. You inherited a "god module" of 4,000 lines. What's your refactor plan?**
**Answer:** Map resources to domains, extract submodules step by step with `moved` blocks, add enable flags at the top level for compatibility, add tests/examples, and version each extracted piece before removing old code.
