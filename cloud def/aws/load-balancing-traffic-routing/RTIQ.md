# RTIQ — AWS Load Balancing & Traffic Routing (Real-Time Interview Questions)

> **Cloud:** AWS · **Domain:** ALB, NLB, Global Accelerator · **Target roles:** SDE-3 · Cloud Engineer · DevOps · DevSecOps · SRE · Platform Engineer · **Reading time:** ~13 min

**How this file is used live:** this round is where interviewers test whether you've ever *debugged* traffic, not just provisioned it. Expect "users see intermittent 504s", "TLS fails for one client", "failover didn't happen". The senior signal is being able to say which layer (DNS, TCP, HTTP, target) owns the symptom.

**Legend:** ⚡ Rapid · 🔍 Deep dive + follow-ups · 🚨 War room · ⚖️ Trade-off debate · 🎯 Senior signal

---

## 1. Application Load Balancer — `application-load-balancer.md`

**⚡ Rapid**
1. **Q:** ALB vs NLB in one line each.
**A.** ALB = layer 7: content-aware routing (path/host/header), WAF, sticky sessions, HTTP/2, gRPC. NLB = layer 4: ultra-low latency, static IPs (per AZ), TCP/UDP/TLS pass-through, millions of flows. If you need static IPs or non-HTTP, it's NLB.
2. **Q:** How do you health check an app correctly?
**A.** A shallow endpoint that proves dependencies, not just "process is up" — `/healthz` returns 200 only if DB and cache are reachable, with a short timeout, sane interval, and `unhealthy_threshold` tuned so transient blips don't drain nodes. A too-strict health check causes cascading outages; a too-lax one keeps serving dead nodes.
3. **Q:** Where do you terminate TLS?
**A.** At the ALB with an ACM certificate, then re-encrypt to targets if the app handles TLS. Key rule: never leave a listener on HTTP without a redirect, and don't terminate at both layers without a reason.
4. **Q:** What's the default idle timeout and why does it matter?
**A.** 60 s. If the app holds requests longer (long polling, big uploads), you get 504s — raise `idle_timeout` *and* the app/server keep-alive together, or one side closes first and clients see sporadic errors.

**🔍 Deep dive**
5. **Q:** Design routing for a multi-tenant SaaS with 40 services behind one ALB.
**A.** Host-based rules per tenant domain → path-based rules per service → target groups. Use listener rules with priority ordering, wildcard certs or ACM multi-SAN, WAF at the ALB, and CloudFront in front for caching/DDoS. Watch the rule limit and keep rules generated by IaC so tenant onboarding is a PR.
**↳ Follow-up:** "A rule change broke a tenant at 2 a.m. — how do you prevent that?"
**A.** Rule changes go through the same pipeline as code: staging ALB with synthetic checks per tenant, canary on the new rule with a weighted target group, and automated rollback on 5xx alarm.
6. **Q:** Sticky sessions — when do you use them and what's the cost?
**A.** Only for legacy stateful apps; they break even distribution and make autoscaling/rolling deploys worse (a node can be "healthy but overloaded"). Modern answer: externalize state (Redis/DynamoDB) or use consistent hashing/JWT affinity.
7. **Q:** How do you do zero-downtime deploys behind an ALB?
**A.** Rolling with deregistration delay + connection draining, or weighted target groups for blue/green and canary. Health check must reflect readiness; new targets must be in a *separate* target group (or a new ALB/ASG) so mixed-version traffic is intentional, not accidental.
8. **Q:** What's the difference between `ELB 5xx` and `target 5xx` metrics?
**A.** `HTTPCode_ELB_5xx` = the LB itself failed (no healthy target, timeout, rule error, target group misconfig). `HTTPCode_Target_5xx` = your app returned an error. The split is the fastest triage decision in the whole round: LB-side = infrastructure/health/config, target-side = application.

**🚨 War room**
9. **Q:** Users report intermittent 504s on one path only. Walk through it.
**A.** Metrics first: `TargetResponseTime` p99 and `HTTPCode_ELB_5xx` vs target 5xx. If ELB 5xx with no target error → idle timeout or all targets unhealthy. One path only → check that service's target group, its health check, and whether the request is long-running. Then confirm with target-side logs and correlation IDs.
10. **Q:** All targets show unhealthy but the app is definitely up. What are the three most likely causes?
**A.** (1) Security group on targets doesn't allow the LB's SG on the health-check port. (2) Health-check path/port wrong or returns non-200 (auth redirect to login = "unhealthy"). (3) App binds to 127.0.0.1 instead of 0.0.0.0. Then check NACLs and, rarely, the target's own TLS/cert mismatch.
11. **Q:** TLS works for browsers but fails for an Android client and a Java client. Why?
**A.** Cipher/version mismatch — security policy is too strict for older clients, or you enabled TLS 1.3-only expectations while the client offers 1.2 with old ciphers, or SNI is missing on the client (old Java). Fix by choosing a policy that matches your client matrix and moving clients forward on a schedule.
12. **Q:** Latency doubles at exactly every 5 minutes. Suspicious?
**A.** Look for scheduled jobs, maintenance windows, a cron on one target, connection-pool/keep-alive cycling, or a health check storm. Also check for a single-AZ target group where one node does all the work; and check cross-zone load balancing is enabled.
13. **Q:** You deployed behind the ALB and now see 502s. What changed?
**A.** Target closed the connection mid-response (app crash/OOM), protocol mismatch (ALB sending HTTP/1.1 to an HTTPS-only target or a gRPC backend on an HTTP listener), or the target's response exceeded size/time limits. Compare a working node's config to a failing one — usually a rollout left mixed versions.

**⚖️ Trade-off**
14. **Q:** ALB → NLB in front, or ALB alone?
**A.** NLB in front of ALB (or NLB with static IPs) when you need fixed IPs for allow-listing, ultra-low latency, or non-HTTP protocols. Costs another hop and complexity; don't add it without one of those requirements.
15. **Q:** WAF on the ALB or on CloudFront?
**A.** CloudFront for volumetric/DDoS and geo rules (and cheaper inspection closer to the edge); ALB if you don't use CloudFront or need ALB-specific integration. Many run both with different rule sets.
16. **Q:** One big shared ALB vs an ALB per service?
**A.** Shared ALB is cheaper and simpler for host/path routing, but couples failure domains and hits rule limits; per-service ALBs isolate blast radius and let teams own config. Standard compromise: shared edge ALB for public traffic, per-service for internal/east-west.

**🎯 Senior**
17. **Q:** You're asked to cut 30% off ALB/LB cost with no reliability regression. Plan?
**A.** Right-size LCUs (fewer, larger ALBs where rules allow; check cross-zone data charges), move idle/internal traffic to ALB instead of NLB, cache at CloudFront to cut LCU-billed requests, remove unused listeners/target groups and idle LBs, and turn on access-log-driven analysis to find chatty health checks and over-frequent polling.

**🎯 Senior signal:** distinguishing LB-5xx from target-5xx, quoting idle timeout vs keep-alive interaction, and knowing the SG-for-health-check gotcha puts you above the pack immediately.

## 2. Network Load Balancer — `network-load-balancer.md`

**⚡ Rapid**
1. **Q:** Why would you choose NLB over ALB?
**A.** Static IPs / Elastic IPs, TCP/UDP/TLS protocols, extreme throughput and ultra-low latency, or preserving the client source IP end-to-end. Also for non-HTTP protocols (databases, MQTT, gRPC over h2 with pass-through).
2. **Q:** How does NLB preserve client IPs?
**A.** In TCP mode the client IP is passed to targets natively (targets must allow the client CIDR, not the LB's). With an ALB behind, you need Proxy Protocol v2 or the ALB's `X-Forwarded-For`.
3. **Q:** Cross-zone load balancing on NLB — default?
**A.** Off by default (you pay for cross-AZ data if you enable it). ALB has it on by default and free. Knowing the asymmetry is a good detail to volunteer.
4. **Q:** Health checks — how do they differ from ALB?
**A.** TCP (port open), HTTP/HTTPS (synthetic), or UDP-based checks. NLB can't do L7 path logic, so it will happily keep sending traffic to a target whose app is broken but whose port is open.

**🔍 Deep dive**
5. **Q:** Your NLB targets are all healthy but users see failed connections. Diagnose.
**A.** Port-up-but-app-dead (add HTTP health checks), target security group not allowing the client range (source IP preservation means the SG must allow clients, not the LB), or a target group with a single AZ and a zone-level issue. Also verify the client isn't hitting a stale DNS record for the old NLB IP — NLBs keep the same IPs, which is a feature and a trap when migrating.
6. **Q:** How do you give a partner a fixed IP range to allow-list, with HA?
**A.** NLB with one Elastic IP per AZ across ≥2 AZs, and tell the partner to allow the whole set. Document that a single IP can go unhealthy during a failover; allow-listing only one IP is a common integration bug.
7. **Q:** How do you terminate TLS on NLB vs pass through?
**A.** Terminate on the NLB to use ACM and ALB-style SNI, or TCP pass-through to keep E2E encryption (needed for mTLS to the app). Regulated/financial environments often require pass-through, so the app owns its certs and mTLS.
8. **Q:** How do you do blue/green with an NLB that can't do weighted routing?
**A.** NLB doesn't support weights — use DNS (Route 53 weighted), a second listener/port, or put an ALB behind it for weighted target groups. This is a favourite trap question; the honest answer is "design the routing layer for the rollout you need".

**🚨 War room**
9. **Q:** After an AZ failure, half the connections fail rather than being redistributed. Why?
**A.** Cross-zone load balancing is disabled, so each AZ's NLB node only routes to targets in its own AZ; when AZ-a's node is gone, clients still resolving to that IP fail until DNS health checks update. Mitigation: enable cross-zone (accept the data cost) and use ≥3 AZs.
10. **Q:** Latency spikes on a UDP service fronted by NLB. Where do you look?
**A.** Target-side packet drops/queue (check the app's receive buffer), MTU/fragmentation issues, health-check-induced flapping, and whether a single flow is pinned to one target (UDP has no connection spreading across targets unless you use multi-flow/quic-aware design). Also confirm no DDoS/volumetric traffic silently saturating the node.
11. **Q:** A migration moved the DNS name to a new NLB and some clients are still hitting the old one after a week.
**A.** Clients pinned by long DNS TTLs, hardcoded IPs in configs/firewalls, or LB-side allow-lists. Fix: keep the old NLB answering for a grace period with a redirect/health response, lower TTLs *before* migrations, and hunt hardcoded IPs in the repo.

**⚖️ Trade-off**
12. **Q:** NLB (L4) with app-level routing vs ALB (L7)?
**A.** If you need content routing, WAF, or auth at the edge, ALB is the tool; NLB is the right pick for protocols/latency/static IPs. Cost of the wrong pick: either missing L7 features implemented badly in the app, or unnecessary complexity/latency.
13. **Q:** Preserving source IP: NLB pass-through vs ALB + `X-Forwarded-For`?
**A.** Pass-through gives the true IP at L4 with no header trust issues, but the app must handle per-client connections. XFF works at L7 but requires the app to trust only the LB and to parse headers — and breaks if another proxy is introduced.
14. **Q:** One NLB with many listeners vs many NLBs?
**A.** Fewer LBs = fewer endpoints to secure and lower cost; many LBs = isolation per protocol/tenant. Watch per-LB limits and keep network boundaries (e.g. internal vs public) separate.

**🎯 Senior**
15. **Q:** How do you size and cost-justify an NLB-based edge for a high-throughput ingest service?
**A.** NLCU = new connections/flows + active flows + processed bytes. Model peak flows/sec and bytes/sec from load tests, add headroom, and compare against the ALB option (LCU-based) plus cross-zone data costs. Include a DDoS/Shield Advanced consideration for public ingest.

**🎯 Senior signal:** volunteering that source-IP preservation changes the target's security-group rules — and that NLB has no weighted routing — signals hands-on operation rather than documentation knowledge.

## 3. Global Accelerator — `global-accelerator.md`

**⚡ Rapid**
1. **Q:** What problem does Global Accelerator actually solve?
**A.** It moves clients onto the AWS global backbone at the nearest edge location using anycast static IPs, cutting internet-path variability (packet loss, circuitous routes) — better than routing over the public internet from a distant client.
2. **Q:** How is it different from CloudFront?
**A.** CloudFront caches content at the edge (HTTP/S, cacheable). Global Accelerator doesn't cache; it's a TCP/UDP accelerator for dynamic, non-cacheable, or non-HTTP traffic (gaming, VoIP, gRPC, SSH, MQTT).
3. **Q:** Does Global Accelerator give you static IPs?
**A.** Yes — two anycast IPv4 (and IPv6) addresses that are global and permanent, ideal for allow-listing and partner integrations without geo concerns.
4. **Q:** What endpoints can sit behind it?
**A.** ALB, NLB, EC2, and Elastic IPs, in one or more regions/AZs. Endpoint groups map to regions with traffic dials for weighting.

**🔍 Deep dive**
5. **Q:** How does failover work and how fast is it?
**A.** Health checks per endpoint group; unhealthy endpoints are removed and traffic re-routes to the next best region — typically within seconds (sub-30 s), and independent of DNS TTL because clients hold the anycast IP. That's the differentiator vs Route 53 failover, which depends on client DNS caching.
6. **Q:** When would you use traffic dials and endpoint weights?
**A.** Gradual regional migrations (dial down a region), canary a new region, or shape traffic during capacity events. Combined with client affinity, it gives you a controlled regional rollout without touching DNS.
7. **Q:** How do you handle client affinity?
**A.** Enable client IP affinity so a client sticks to an endpoint (good for UDP sessions/gaming); disable it when you want even distribution and fast failover. It interacts with your app's session handling — decide deliberately.
**↳ Follow-up:** "Which is better for a session-heavy TLS service?"
**A.** Affinity reduces re-handshakes and session-state churn, but slows rebalancing during failures. For TLS stateful services, affinity plus a short drain is usually right; for stateless HTTP, leave it off.

**🚨 War room**
9. **Q:** You enabled Global Accelerator and p99 latency improved but one region's users report instability.
**A.** Check that region's endpoint group health (it may be receiving traffic while degraded — dial it down), verify the endpoint's own capacity, and confirm clients aren't stuck on affinity to a failing endpoint. Also validate that the accelerated path isn't bypassing a WAF/inspection point the region relied on.
10. **Q:** Costs spiked after enabling it. Why, and what do you do?
**A.** GA bills a fixed hourly fee plus data transfer premium over normal egress, plus DT-Premium per GB processed. Verify you're not accelerating traffic that doesn't benefit (bulk downloads, cacheable content, internal-only traffic), use endpoint group dials to reduce cross-region flows, and remove idle accelerators.
11. **Q:** A partner allow-lists your two GA IPs; a regional failover happens and they see no errors. Is anything wrong?
**A.** No — that's the feature: same anycast IPs regardless of region. But verify their side isn't pinning to one IP's DNS/health assumptions, and confirm your endpoint group failover actually moved traffic (check flow logs and endpoint health).

**⚖️ Trade-off**
13. **Q:** Global Accelerator vs CloudFront vs Route 53 latency-based routing for a global app?
**A.** Cacheable content → CloudFront. Non-cacheable dynamic/TCP/UDP with strict global latency → Global Accelerator. Cheap DNS-level steering where TTL tolerance is fine → Route 53 latency/geoproximity. Many architectures put CloudFront in front for HTTP and GA for the real-time protocols.
14. **Q:** Is GA worth it if your users are all in one region?
**A.** Usually no — the benefit comes from long-haul paths and multi-region failover. Justify with measured p99/packet-loss deltas, not instinct.

**🎯 Senior**
15. **Q:** Design a global active-active ingress with sub-second regional failover for a payments API.
**A.** GA with endpoint groups per region (dials + health checks) → ALB per region → multi-AZ targets; Route 53 health-checked records as a secondary path; idempotency at the app layer; data replication with a clear consistency story; and continuous synthetic checks per region feeding both automation and the on-call dashboard.

**🎯 Senior signal:** "GA doesn't cache, it accelerates" plus knowing failover is DNS-independent are the two facts that mark real experience.
