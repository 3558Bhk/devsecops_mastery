# Terraform Modules (Azure) — Interview Questions

> **Cloud:** Azure · **IaC Tool:** Terraform · **Levels:** Case A (Basic) · Case B (Advanced/Senior) · Case C (Scenario) · **Reading time:** ~5 min

---

## Case A — Basic

**A1. What is a Terraform module?**
**Answer:** A directory of `.tf` files that groups related resources. The root module is your working directory; child modules are called from it.

**A2. How do you call a child module?**
**Answer:** `module "network" { source = "./modules/network" ; address_space = ["10.0.0.0/16"] }` — `source` points to a local path, registry, or Git repo.

**A3. What does the `source` argument accept?**
**Answer:** Local paths, the public Terraform Registry (e.g. `Azure/network/azurerm`), private registries, Git URLs (with `ref` for tags), and HTTP archives.

**A4. How do modules pass values in and out?**
**Answer:** Inputs go in via module arguments; outputs come back via the module's `output` blocks, referenced as `module.network.vnet_id`.

**A5. What is the Terraform Registry?**
**Answer:** A public catalog of providers and modules, including Microsoft/Azure-published modules like `Azure/aks/azurerm`.

**A6. How do you pin a registry module version?**
**Answer:** `source = "Azure/network/azurerm" ; version = "5.0.0"` or a constraint like `~> 5.0`.

**A7. What files conventionally make up a module?**
**Answer:** `main.tf` (resources), `variables.tf` (inputs), `outputs.tf` (outputs), `versions.tf` (required providers), and a `README.md`.

**A8. What is module composition?**
**Answer:** Building larger systems by nesting modules — e.g. a `spoke` module that uses a `network` and `compute` module — each with clean input/output contracts.

**A9. How do you pass a provider into a module?**
**Answer:** Via the module's `providers` argument, e.g. `providers = { azurerm = azurerm.prod }` for a module that should target a specific subscription alias.

**A10. Can you use `count`/`for_each` on a module block?**
**Answer:** Yes — instantiate the module multiple times with different inputs, e.g. one spoke per region or per environment.

**A11. How do you document a module?**
**Answer:** README with purpose, usage examples, and inputs/outputs tables (often generated by `terraform-docs`).

**A12. What is the difference between a module and a workspace?**
**Answer:** A module packages reusable code; a workspace is a separate state for the same code (environment isolation).

**A13. How do you update a module version?**
**Answer:** Bump the `version` constraint and run `terraform init -upgrade`, then `plan` to review the diff.

**A14. What is a module registry namespace?**
**Answer:** The owner/name of a module (e.g. `Azure/network/azurerm`) — community modules live under publishers; your org can run a private registry.

**A15. How do modules isolate variable scope?**
**Answer:** A child module sees only variables declared in it and passed values; it never inherits the caller's variables or locals automatically.

## Case B — Advanced / Senior

**B1. How do you design a good Azure module API?**
**Answer:** Small, typed input surface with defaults; meaningful outputs (resource IDs, names); no hidden dependencies; validation for Azure-specific constraints (naming, region); and versioning. Treat it like a library.

**B2. What is the recommended structure for a large reusable module?**
**Answer:** Nested submodules for concerns (e.g. `modules/vnet`, `modules/nsg`) wrapped by a thin root with enable flags (`count = var.enable_x ? 1 : 0`), so consumers can compose pieces.

**B3. Why pass providers explicitly in multi-subscription setups?**
**Answer:** Modules default to the caller's provider; for resources in another subscription, pass an aliased provider via `providers = { azurerm = azurerm.other }` so the module targets the right place.

**B4. How do `count`/`for_each` on modules change outputs?**
**Answer:** Outputs become collections: `module.spoke["east"].vnet_id`. Use stable keys (map keys, not list indexes) to avoid churn.

**B5. What is the "enable flag" pattern?**
**Answer:** Wrapping optional resources in `count = var.enable_private_endpoint ? 1 : 0` so one module serves many use cases — convenient but can bloat the code; document each flag.

**B6. How do you version Git-hosted modules?**
**Answer:** Tag releases and reference them: `source = "git::https://github.com/org/repo.git?ref=v1.2.0"`. Pin to tags, not branches, for reproducible builds.

**B7. How do you test a module?**
**Answer:** Example root modules run in CI against a sandbox subscription (plan/apply/destroy), plus `terraform validate`, `tflint`, and Terratest for behavior assertions.

**B8. How do you refactor inline Azure resources into a module without downtime?**
**Answer:** Create the module, move resources with `moved` blocks (or `terraform state mv`), verify the plan shows no changes, then remove the inline definitions.

**B9. What are the downsides of deep module nesting?**
**Answer:** Harder to trace values, more outputs to thread through, slower reviews, and provider confusion. Prefer shallow composition with clear naming.

**B10. How do modules handle Azure secrets?**
**Answer:** Mark inputs `sensitive`, never hardcode secrets, and prefer references to Key Vault (`azurerm_key_vault_secret` + `data` lookups) or Key Vault-backed provider config.

**B11. What is a common Azure module publishing workflow?**
**Answer:** Keep the module in its own repo with examples, run CI (validate/lint/test), tag a release, and let teams consume via the registry or Git ref with a pinned version.

**B12. How do you standardize tagging and naming across modules?**
**Answer:** Accept a `default_tags` map and a `naming_prefix` input in every module, merge them into resources in a `locals` block, and document the convention so all Azure resources are consistently tagged.

## Case C — Scenario

**C1. You have four similar Azure landing zones. How do you DRY them up?**
**Answer:** Build a `landing-zone` module (VNet, subnets, NSGs, peering) parameterized per zone, instantiate with `for_each` over a map, and vary inputs via tfvars — no copied directories.

**C2. A community module you rely on broke your plan after an update.**
**Answer:** Pin the last working version, review the changelog, adapt inputs or wrap it with your own adapter module, then test the upgrade in a sandbox before bumping the constraint.

**C3. You need the same VNet module in two Azure regions.**
**Answer:** Call the module twice with different `location` (and names) — or use aliased providers if subscriptions differ — keeping per-region state separate.

**C4. A consumer keeps misconfiguring an input (e.g. an invalid subnet range).**
**Answer:** Add `validation`/`precondition` checks with clear messages, improve examples, shrink the API to what's needed, and version the module so changes are opt-in.

**C5. Management wants your internal module shared without publishing publicly.**
**Answer:** Use a private registry (Terraform Cloud/Enterprise or GitLab) or reference the Git repo by tag over SSH, and document versioning so teams pin releases.

**C6. You inherited a 3,000-line "everything" module. What's your plan?**
**Answer:** Map resources to domains, extract submodules step-by-step with `moved` blocks, keep a compatibility layer with enable flags, add tests/examples, and version each extraction before deleting old code.
